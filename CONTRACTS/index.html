    API and Data Contracts

    This document defines the backward-compatibility guarantees for data structures and CLI outputs used by enterprise integrations, IDEs, and editor-plane agents.

    release_docs_current_tag: v1.124.0

    0. The completeness contract (governs every section below)

    Every tg answer is either complete, or it names exactly how it is incomplete and whether the caller can do anything about it.

    This is the one promise the rest of this document implements. It exists because tg's primary caller is an AI agent, and an agent cannot tell a genuinely empty result from a silently truncated one. "No callers found" acted on in good faith deletes working code. A result that is smaller than the question it claims to answer, with no marker saying so, is a wrong answer -- not a smaller one.

    Three obligations follow, in priority order:

    • P1 -- no silent loss. A command that drops an entry it could not read must say so. Never return a shortened collection with a success marker. Where dropping the entry would corrupt the answer rather than shrink it, fail closed instead: refuse, and leave the caller's state untouched.
    • P2 -- actionable disclosure. Naming the incompleteness is not enough; the caller needs to know whether it is theirs to fix. A budget cause (scan_limit, deadline) is remediable -- raise the knob. An unreadable path is not: no budget increase makes it readable. Handing over the wrong knob is its own defect class, and the reason unreadable_path OUTRANKS every budget cause when both fire.
    • P3 -- surface agreement. The CLI, the --json envelope, the exit code and the MCP tools must tell the same story about the same run. A renderer must never change the answer.

    1. Configuration (sgconfig.yml)

    The root-level keys and structure of sgconfig.yml are guaranteed to be stable within a major version. Unrecognized keys will be ignored rather than causing fatal errors to allow progressive rollout of new configurations.

    2. AST Cache (project_data_v6.json)

    The schema of the .tg_cache/ast/project_data_v6.json cache is versioned within its filename. - Backward compatibility is NOT guaranteed across major/minor versions. - If the schema changes (for example to v7), tensor-grep will automatically invalidate older cache files and rebuild them transparently.

    3. Text-search compatibility

    The stable text-search compatibility contract is the validated compatibility set covered by the parity suite and contract benchmark runner. tg search --help may expose more rg-style flags, but only the rows below and explicitly named deterministic edges are part of the public rg-compatibility claim.

    Current validated rows: - -i/--ignore-case - -v/--invert-match - -C/--context - -A/--after-context - -B/--before-context - -g/--glob - -l/--files-with-matches - --files-without-match - tensor-grep aggregate --json - ripgrep JSON Lines via explicit --format rg --json - --ndjson - -F/--fixed-strings - -w/--word-regexp - -m/--max-count - --files - -t/--type - -./--hidden - -L/--follow - -S/--smart-case - -n/--line-number - --column - -c/--count - --count-matches - -a/--text - -0/--null - -U/--multiline - --multiline-dotall

    Character-for-character identity is not required for help formatting, but command presence, supported rows, accepted normalization, and the deterministic parity corpus are part of the public contract. Additional rg-style flags may be exposed in tg search --help, but they are not covered by the stable compatibility claim until they are added to the contract suite and benchmark runner.

    Agent automation contracts: - tg search PATTERN defaults to the current directory when no path is provided. - Invalid regex syntax exits as an error distinct from no-match and emits a diagnostic that recommends --fixed-strings for literal searches. - tg search --json emits a valid tensor-grep aggregate JSON object even when there are zero matches. - tg search --format rg --json forwards to ripgrep and emits rg JSON Lines events without a tensor-grep envelope for tools that require rg's event schema. - tg search --files-with-matches stays root-based on the ripgrep path instead of expanding large candidate-file lists into the Windows process argument vector, and plain path-list output emits one trailing line separator only. - tg search with --format rg is a public exact ripgrep-style text formatter for automation that needs rg-shaped stdout. Pair it with --sort path when deterministic path ordering matters across backends. - The native front door treats --format rg as a no-op for rg-compatible text output and preserves --sort path when forwarding to ripgrep. Non-rg --format search output remains a Python CLI formatting surface. - The public native front door must not reject flags advertised by the public Python CLI. It may execute the request natively, forward to ripgrep, or route to the Python sidecar, but sidecar routing must be intentional and covered by a public-native regression test. - Root shortcut invocations with option-first common search flags, including tg -t js PATTERN PATH and tg --count-matches PATTERN PATH, are treated as tg search ... and must preserve those flags through native, ripgrep, or sidecar routing instead of falling back to positional-only parsing. - Cached-session requests must stay on the warm path by default. One-shot tg session ... commands and daemon-routed session requests validate files captured in the session snapshot with direct size/mtime checks and must not walk the full repository merely to check for added files. Added-file discovery belongs to explicit refresh paths: tg session refresh ... and requests that opt into --refresh-on-stale. A session opened on a repo with zero context files is still subject to added-file detection on those explicit paths. Daemon response-cache hits intentionally use detect_added_files=False before serving cached context-render / edit-plan payloads so truncated implicit sessions stay fast; new files under the repo are invisible to response-cache invalidation until refresh_on_stale or tg session refresh. Daemon stats exposes response_cache_stale_detection = "snapshot_mtime_only" and response_cache_added_file_detection = false so agents can see the tradeoff without guessing. The 5 symbol commands (defs / impact / refs / callers / blast-radius) are also response-cached: a repeated warm request with an identical symbol/provider/max-tests/max-depth/max-repo-files is served straight from the daemon's response cache instead of re-running the caller-scan or blast-radius graph walk. Unlike context-render / edit-plan, the symbol-command gate honors the request's real refresh_on_stale flag -- added-file detection included -- before trusting a cache hit, because a caller/blast-radius answer that silently omits a newly-added call site is a wrong answer, not merely a stale one; a genuinely new file (or a modified/removed tracked file) busts a symbol-command cache entry on the very next request. Session edit-plan graph ranking, test matching, and blast-radius metadata must stay bounded to selected context budgets and report the bounded radius scope in edit_plan_seed.blast_radius_scope; daemon requests should keep a short connect probe while allowing longer edit-plan/context responses. Top-level native-provider tg context-render and tg edit-plan may reuse an already-running daemon and create an implicit session keyed by root and max_repo_files so repeated agent-loop calls hit daemon response-cache counters without reusing a smaller scan budget for later larger requests. tg session list and tg session daemon status should discover nearby session scopes when the requested/current root has no direct session metadata, and JSON output should expose whether discovery was used. Daemon-routed relative paths are resolved against the daemon root before session lookup so tg session edit-plan ID . --daemon works from the served project root and does not accidentally target the daemon process working directory. - tg checkpoint list PATH must keep default discovery nearby and bounded: direct scope, ancestors, and immediate non-generated children only when the direct scope is empty. Recursive child-scope discovery is opt-in through --discover; generated/cache roots require the explicit --discover-full mode. Explicit recursive discovery may cache fingerprinted checkpoint index paths for repeat calls, but create and undo must invalidate ancestor discovery caches so agent loops do not reuse stale scope lists after checkpoint state changes. - tg search --files remains a generated-root guardrail surface. The native front door may route it to the Python sidecar so broad generated-root refusal, --glob, --type, --max-depth, and --allow-broad-generated-scan keep the same public semantics. - tg search --multiline / -U, --multiline-dotall, and -0/--null must be accepted by the native front door and forwarded to the backend that preserves rg-compatible behavior for the requested output mode. - --sort path is the deterministic contract for --files-with-matches, --files-without-match, --replace, and path-list automation. The parity suite also checks match, no-match, parse-error, and binary-skip exit-code behavior. - Default output ordering for root-scale --files-with-matches, --count, and --force-cpu is a semantic result parity contract, not a golden stdout ordering contract. Use --sort path when automation needs deterministic path ordering across backends. - Broad generated roots such as .claude are routed through Python guardrails instead of rust-first/native passthrough so generated .claude/context snapshots can be pruned by default. - Unbounded broad generated-root scan requests are refused with exit code 2 when hidden file-list scans contain generated, cache, or dependency child directories, or when content searches directly target a generated/cache/dependency root. Explicit --no-ignore content searches over an ordinary project root follow ripgrep and may traverse ignored generated child directories; direct generated roots still require a scoped path, --glob, --type, --max-depth, or --allow-broad-generated-scan. Unbounded searches against a parent that looks like a multi-project workspace root are also refused before the broad walk. tg scan / MCP ruleset scans apply the same safety posture to AST/ruleset workflows: direct temp, AppData, user-home, filesystem-root, generated/cache/dependency, or multi-project workspace roots must be scoped to a project/subdirectory, bounded with --max-depth (and optionally --glob / --type), or explicitly opted in with --allow-broad-generated-scan before any scanner walk begins. - tg search honors a root .ignore/.gitignore/.rgignore uniformly, including in a non-git directory, where raw rg's own require_git default makes an un-flagged .gitignore inert. This is a deliberate, permanent divergence from raw rg in that one cell, not an unintended parity gap: --no-ignore and --no-ignore-vcs opt back out, matching rg's own documented per-flag scope. - An implicit-path tg search (PATH omitted, defaulting to the current directory per the earlier bullet) whose directory WALK exceeds an internal file-count ceiling (1500 files visited, counted independent of match count or glob/type selectivity) is refused with exit code 2 and an actionable message instead of running unbounded. This guard runs as the first statement of execute_ripgrep_search itself, so it applies uniformly across every entry point that can reach that function -- the full Python CLI, the standalone native binary's default search front door (including its -e/--regexp form), the positional CLI, tg-search-fast, and the PyO3 FFI bridge -- rather than one call site that a different entry point could bypass. An explicit, deliberately-scoped PATH is never refused regardless of size. - tg search --type-list prints a built-in fallback list when no ripgrep or standalone native binary is available. --pcre2-version follows ripgrep semantics and exits with an error when no PCRE2-capable backend is available. - tg ast-info --json exposes AST language identifiers via {"languages": [...]} for agent discovery without help-text scraping. - Read-only tg run follows search-style no-match semantics: zero AST matches exit 1 while successful matches exit 0; parse/configuration errors remain distinct non-zero failures. On Windows, if the received pattern is still wrapped in single quotes, tg run warns that cmd.exe treats those quotes literally and suggests double quotes for cmd.exe. - Native exit-code honesty: 0 found, 1 genuinely no match, 2 error or incomplete. A child process (ripgrep, the Python sidecar) that is killed by a signal or crashes with a negative NTSTATUS exits 2, never 1; tg run command errors (for example Path not found) and --index search failures exit 2; a --apply that fails part-way exits 2 and its error lists files_written and files_failed (written files are NOT rolled back, and a failed file may be partially modified). --index decodes non-UTF-8 files lossily (U+FFFD in match text) instead of aborting the search. -c/--count combined with --json or --ndjson now emits only the normal structured payload (with match_counts_by_file) instead of plain path:count lines mixed into JSON; this is a payload-size increase for count users. The did-you-mean nearest[] list is ranked by edit distance (closest first, alphabetical tie-break) BEFORE the cap of 5 in both front doors. - On Windows, PowerShell automation should invoke tg or tg.ps1 for regex metacharacters. PowerShell double quotes expand $NAME-style values before tensor-grep receives argv, so literal patterns containing $ should use single quotes or escape $ as `$. Direct .cmd invocation from PowerShell is not a safe argv-preserving contract for unescaped metacharacters such as | because cmd.exe parses the line before the batch wrapper receives arguments; tg.cmd is for cmd.exe. - The quoted multi-word no-match pattern case from cmd.exe, direct tg.cmd, and Python subprocess.run([...]) is a public launcher contract. The launcher must preserve the phrase as one argv item and must not turn it into a shorter false-positive search plus bogus paths. - Stable managed install scripts should prefer the matching release-native CPU tg binary as the public front door when the GitHub release asset is available, set TG_SIDECAR_PYTHON for Python-backed commands, set TG_NATIVE_TG_BINARY for the sidecar, and fall back to python -m tensor_grep when no native asset exists.     Context and edit-planning contracts: - context-render and MCP context output must not let edit_plan_seed.primary_file, navigation_pack.primary_target.file, rendered source sections, and follow-up reads contradict each other. - context_consistency reports whether the primary file is included, whether rendered context matches the primary target, whether confidence was downgraded, and why a primary file was omitted from rendered budget. - The default JSON/LLM render profile includes executable body lines for selected functions. Compact rendering can remove comments, docstrings, blank lines, type-only imports, and boilerplate, but it must preserve matched behavior unless the caller requests a summary-only profile in a future contract. - Validation command hints use validation_plan[].detection with values of detected, heuristic, or generic. JavaScript package-manager commands require package.json evidence; Python commands require tests, project markers, or Python layout evidence; omit commands entirely when no runner evidence exists instead of inventing npm test or uv run pytest. - Validation hints must align with the selected primary target language unless verified cross-language dependency evidence exists. validation_alignment records whether validation remained aligned or whether incompatible commands were filtered; a TypeScript primary target must not silently receive pytest-only validation, and a Python primary target must not silently receive JS-only validation. - Edit validation command templates support $file and {file} placeholders. For applied rewrites, placeholders are replaced with each edited file path and the command runs once per edited file; commands without a file placeholder run once against the original target working directory. Examples should quote the placeholder, such as python -m py_compile "$file", so Windows paths with spaces remain one argv item. - edit-plan and context-render JSON both expose top-level validation_commands copied from navigation_pack or edit_plan_seed for quick agent access. Agents should not need command-specific parsing just to find the recommended validation command list. edit-plan JSON additionally exposes a top-level validation_plan (the structured step list -- command, confidence, detection, runner, scope, optional target -- copied from edit_plan_seed.validation_plan), matching the shape agent JSON already surfaces at its own top level; this is additive and never removes or mutates validation_commands. - edit-plan JSON also exposes top-level confidence ({overall, downgrade_reasons}) and ask_user_before_editing ({required, reasons}), matching the shape agent JSON already surfaces at its own top level.     The JSON schemas emitted by tensor-grep search --json, tensor-grep search --ndjson, and the documented harness/editor-plane flows are considered public APIs. tensor-grep search --format rg --json is a compatibility route for ripgrep's JSON Lines event schema, so consumers should use rg's event contract rather than the tensor-grep envelope for that mode. - Existing fields (for example file, line, match, context) will not be renamed or removed without a major version bump. - New fields may be added in minor versions. - Consumers should ignore unrecognized JSON fields. - result_incomplete: true payloads additively carry incomplete_reason_class alongside the free-text incomplete_reason -- a closed vocabulary ("unreadable_path", "scan_limit", "deadline", "timeout", "workspace_root_refused", "coverage_gap") an agent can branch on WITHOUT string-sniffing the human-readable reason. It is omitted entirely (not null) on a complete result, matching result_incomplete/incomplete_reason's own omit-when-complete convention, so a complete search stays byte-identical. It is present on the two Python-implemented tg search routes that can set result_incomplete: the rg-backend route (rg's own soft per-path exit-2 error, always "unreadable_path"; a timed-out rg subprocess, "timeout") and the Python CPUBackend fallback route reached when native delegation is refused or unavailable -- no compiled native tg binary on the machine, or a flag native delegation does not support (a directory scan that hit an unreadable path, "unreadable_path"; the scanner's own defensive entry-count budget, "scan_limit"; the native per-file wall-clock budget, "timeout"). A multi-project workspace-root refuse (Python CLI _emit_broad_scan_refusal) uses "workspace_root_refused" so agents do not confuse a parent-workspace refuse with a file-cap truncation; other broad-scan ceilings retain "scan_limit". The compiled native/Rust engine also emits these fields. --cpu, --force-cpu, and --json are themselves native-delegation TRIGGERS (bootstrap.py), so on a normal install with the native tg binary present, tg search ... --cpu --json is answered by the compiled Rust front door reporting routing_backend = "NativeCpuBackend". That route counts unreadable entries into SearchStats.walk_errors (native_search.rs, struct SearchStats), declares the triple on struct NativeJsonOutput and stamps it in emit_json_matches (same file), and exits 2 when the count is non-zero in run_native_search_with_optional_rg_fallback (main.rs) -- the same disclosure and the same exit code as rg on the same directory. The serial-walk collector was the last producer without a count channel and now carries one (WalkedFiles, #276 slice B3). - Route support must be established from the documented backend and its envelope contract, not inferred from an absent reason class alone. Compiled single-pattern CPU output uses NativeJsonOutput; multi-pattern -e/-f routes use SearchResultJson and SearchSummaryNdjson; CUDA output uses GpuNativeSearchResultJson and GpuNativeSearchStats::walk_errors. These producers share incomplete_envelope_fields. The route name alone does not distinguish single-pattern and multi-pattern native CPU execution. - resolution_gaps (symbol commands: defs, refs, callers, source, impact, blast-radius*, imports, importers, file-api) lists every file the symbol graph could not fully read or cover. Each entry carries language, reason, files_affected, files_sample (up to 5, root-relative), remediation and affects_completeness in {"never", "when_empty", "always"}. Kinds: no registered extractor / no reverse-import resolver (never), grammar not installed (when_empty), file over TENSOR_GREP_MAX_PARSE_BYTES, Python syntax error (or RecursionError/NUL byte at parse time), unreadable file, and not-valid-UTF-8 (undecodable bytes were replaced) -- all when_empty. A when_empty gap flips result_incomplete (exit 2, incomplete_reason_class: "coverage_gap") ONLY when the answer is EMPTY, because an empty answer is the one case where silence reads as "proven absent"; a non-empty answer keeps exit 0 and discloses the gap. An earlier cause (a scan limit, a deadline, an unreadable path) keeps incomplete_reason/class/remediation; the gap stays listed. blast-radius, blast-radius-render and blast-radius-plan additionally stamp coverage_gap_limit (possibly_truncated, reason, files_sample, remediation) when a gap blocked the answer, which is what their exit-2 gate and banner read. Missing-grammar behavior: a defs/refs/callers lookup whose grammar is missing and whose answer is empty now exits 2 : an empty answer under a missing grammar is unverified, not absent. tg diff-impact adds unparsed_changed_files (changed files whose symbols could not be extracted) and tg search --enrich-ast marks matches in unparseable files with enclosing_symbol_status: "unparsed". - incomplete_reason_class matters because the causes are NOT equally remediable: "scan_limit"/"deadline"/"timeout" are genuinely fixable by raising a budget (--max-repo-files, --deadline, TG_RG_TIMEOUT_SECONDS/TG_DIR_SCAN_MAX_ENTRIES) or narrowing scope; "workspace_root_refused" is remediable by scoping (--glob/--type/--max-depth/explicit path) or --allow-broad-generated-scan, never by raising a file-cap; "unreadable_path" is NOT budget-remediable -- the path needs to become readable, or the search needs to be scoped away from it. See the exit-code bullet below for the same distinction applied to tg search's exit-2 retry guidance. - The MCP tg_search tool exposes the SAME remediability distinction on its own scan_limit object, from contract version 1.5.0. When -- and only when -- the scan was actually truncated it additively carries truncation_cause ("scan_limit" / "unreadable_path" / "unknown"), budget_remediable (bool), and, when non-zero, unreadable_path_count. A complete scan emits none of them and stays byte-identical to contract 1.4.0. budget_remediable is the field a caller should branch on before advising a retry: it is false for "unreadable_path" (no max_repo_files value makes a denied directory readable) and ALSO false for "unknown", because an unrecognised cause must never be answered with "raise the limit" -- guidance about whether a signal can be trusted is an allow-list, never a deny-list. TWO known asymmetries, deliberately recorded rather than papered over: (1) possibly_truncated: true can still appear with NO truncation_cause, because the per-file max_repo_files cap and the native-walk deadline set it independently of the DirectoryScanner, so "truncated implies a cause is present" is NOT an invariant a client may rely on; (2) this truncation_cause vocabulary is NOT identical to the CLI's incomplete_reason_class above, and the two must NOT be unified : MCP's truncation_cause has "unknown" where the CLI raises loudly. From contract 1.6.0 the MCP tg_search/tg_ast_search payloads ALSO carry the CLI-family incomplete_reason_class at top level, additively and only when the cause is classifiable -- both native-walk deadline paths emit "deadline", and a broad-scan refusal emits "scan_limit". An AST-backend failure sets result_incomplete and deliberately emits NO class, because a backend fault is none of the four members and the vocabulary is an allow-list. An ABSENT class therefore means "cause not classifiable", NEVER "scan complete" -- completeness is carried by result_incomplete alone. From contract 1.7.0 the same budget_remediable flag ALSO appears on the scan_limit / output_limit of every build_repo_map-backed tool -- tg_repo_map and the tg_session family -- because those handlers return the CLI payload VERBATIM. Same additive rule as above -- emitted only on a CAPPED scan, absent and byte-identical on a complete one -- and the same single allow-list (cli/incompleteness.py) supplies the value on both surfaces, because two copies is how CLI and MCP drift into opposite retry advice. From contract 1.8.0 every MCP tool JSON envelope ALSO carries a unified top-level incomplete: {status: bool, cause: str|None, budget_remediable: bool} object, injected by _inject_mcp_contract_fields (the single choke point that already stamps mcp_contract_version/schema_version on every tool response) via cli/incompleteness.py::unified_incomplete_envelope, so a client can check ONE consistent field regardless of which of the 58 tools it called instead of learning each tool's own surface-specific vocabulary (result_incomplete/truncation_cause/incomplete_reason_class/...). It is DERIVED, never a replacement: every pre-existing field above stays present and byte-identical, incomplete.status mirrors result_incomplete (default False for a tool with no incompleteness concept), incomplete.cause mirrors the free-text incomplete_reason (never the closed-vocabulary class), and incomplete.budget_remediable mirrors the tool's own budget_remediable when status is true and is forced False when it is not. A tool that builds its own incomplete key is never overwritten (setdefault). - result_incomplete alone is NOT a sufficient completeness check. It answers exactly one question -- "was the SCAN cut short?" -- and a payload can therefore report result_incomplete: false with exit 0 while still handing back materially less than it found. An agent that branches only on result_incomplete (or only on the exit code) will read those payloads as complete. Three additional fields carry that information, and their PRESENCE RULES DIFFER -- read each one's rule below rather than assuming a single convention, because "the field is absent" means different things across them: - token_budget (defs / refs / callers / impact, and the agent capsule) -- an OUTPUT cap from --max-tokens. PRESENCE RULE: emitted whenever --max-tokens is in effect, INCLUDING on a complete result, where it reads truncated: false / primary_truncated: false and carries no primary_omitted at all. So unlike the two fields below, the object's presence proves nothing on its own -- you must read primary_truncated. (The sibling omissions envelope is likewise always present, with an empty omitted_sections when nothing was trimmed.) token_budget.truncated says something was dropped for display; primary_truncated says the drop hit the PRIMARY result list, not just secondary sections; primary_omitted is how many primary rows were withheld. omissions.omitted_sections[] names each trimmed section with a reason. This is deliberately NOT a scan truncation -- the analysis ran to completion and only the rendering was capped -- which is why it stays exit 0 and does not set result_incomplete (see the OUTPUT-cap rule above). That distinction is correct and load-bearing, but it means primary_truncated is the ONLY field that will tell you the answer you are reading is a subset. Branch on it. Concretely: tg callers . <symbol> --json can return 1 of 4 callers with result_incomplete: false, not_found: false, exit 0, and token_budget.primary_omitted: 3 -- every one of those is contract-correct, and only the last one is the whole story. Raise --max-tokens (or pass --max-tokens 0) to get the full set. - incomplete_paths_count (compiled-native --json / --ndjson search envelopes) -- how many walk-error EVENTS the search hit, alongside result_incomplete and incomplete_reason_class. Omitted entirely on a complete walk. Despite the name it is NOT a count of distinct paths, and it can exceed one: the walker visits each ROOT you pass, without deduplicating overlapping roots, so tg search PAT . src walks src twice and one unreadable directory under it raises the count twice. With overlapping roots, a failed path can be visited repeatedly, so the number is a faithful count of failed reads rather than a defect -- but a caller that needs "how many distinct places could I not look" must not read this field as that answer. For a genuine per-path count see MCP's unreadable_path_count, which is a different field with different semantics (directory_scanner.py, once per failed os.scandir) and is deliberately NOT unified with this one. - not_found -- asserts the symbol is genuinely ABSENT, and is therefore only meaningful on a scan that finished. It is suppressed whenever the scan was truncated, so not_found: false on an exit-2 payload means "we did not finish looking", NOT "we found it". - output_limit (tg map, tg blast-radius, and the defs / refs / callers / impact symbol commands) -- an OUTPUT cap from --max-files/--max-callers/--max-tests. It describes DISPLAY omissions, never analysis completeness: result_incomplete describes the analysis/scan, and an output-only cap keeps it false with exit 0, disclosing instead via an OUTPUT LIMITED: display omitted N caller(s)/file(s)/test file(s)/import consumer(s); raise --max-* to see more caveat (a trailing note: in text; in --mermaid a tg_output_limited advisory node, distinct from the scan-truncation tg_incomplete node). A capped subset is NOT exhaustive: read the exact omitted_* counts and raise the named knob to get the rest. Only a SCAN truncation (scan_limit/caller_scan_limit/partial/caller_scan_truncated, or a preexisting upstream-stamped result_incomplete: true) exits 2 with a leading INCOMPLETE RESULT warning; when a scan truncation and an output cap are both present the caveat discloses both facts, and the deadline is never masked by the display cap. The general rule, and the reason this list is written out rather than left implicit: a field that a caller must read to detect incompleteness has to be NAMED in this contract, or the contract fails open -- a consumer who does not know the field exists cannot branch on it, and silence reads as completeness. Adding a new truncation or omission channel means adding it here in the same change.

    • A THIRD backend name reaches --cpu --json on a plain pip/uvx install: "RustCoreBackend". The paragraph above describes the machine that HAS the compiled native tg binary, where --cpu --json reports "NativeCpuBackend" (emitted by the Rust binary itself, rust_core/src/routing.rs). A wheel install has no such binary, so the same command is answered by the PYTHON RustCoreBackend class over the tensor_grep.rust_core extension, reporting routing_backend = "RustCoreBackend" / routing_reason = "rust_regex". This is not cosmetic, because the allow-list rule stated above is keyed on these exact strings. A consumer who allow-lists only "CPUBackend" and the rg route will correctly REJECT "RustCoreBackend" (fail-closed, which is the desired direction) -- but will do so while the scan was in fact complete, so the failure mode is a false incompleteness rather than a false completeness. Both names must therefore be in the reader's model: "NativeCpuBackend" = compiled front door, "RustCoreBackend" = Python-over-extension, and neither carries the native-envelope incompleteness fields the rg route and the Python CPUBackend route provide.

    • Two similarly-named count fields mean different things and can legitimately disagree in one payload. scan_limit.scanned_files counts files the repo-map COLLECTION stage actually walked/parsed. deadline_limit.files_scanned counts files the specific deadline-bounded stage got through before the budget expired, against deadline_limit.files_total. A single tg refs ... --deadline 0.1 --json payload can therefore carry scan_limit.scanned_files: 247 and deadline_limit.files_scanned: 0 simultaneously and be internally consistent -- the map was already built, and the reference-scan that consumes it never started. Neither field is a repo-wide total; for "was this complete?" use partial / result_incomplete / the exit code, never a comparison between these two numbers.

    • deadline_limit's scanned/total pairs name WHICH stage ran out of budget; deadline_exceeded alone cannot. deadline_exceeded is a single shared boolean, and several stages read the same clock, so a caller seeing it knows only THAT the budget expired. Each deadline-bounded stage therefore contributes its own pair, emitted additively and only when that stage actually ran: files_scanned/files_total (repo-map collection), caller_files_scanned/caller_files_total (tg callers), reference_files_scanned/reference_files_total (tg refs), importer_candidates_scanned/importer_candidates_total (reverse-import walk), source_candidates_examined/source_candidates_total (definition preference), and test_candidates_scanned/test_candidates_total (the whole-repo test-relevance scorer on the callers/impact/refs paths). A pair's ABSENCE means that stage did not run, not that it completed. test_candidates_* additionally SUMS ACROSS SCANS: tg callers reaches the test-relevance scorer twice when the symbol has callers (the second scan sits behind an if caller_files: guard; tg impact and tg refs reach it once), so a 6-test repo typically reports test_candidates_total: 12, and 6/12 there means the first scan completed and the second never started -- NOT 50% coverage of the repo's tests. Read the pair as "candidate slots walked out of slots this command was going to walk", never as a count of distinct test files. scanned may legitimately be 0 against a non-zero total — the stage was reached and stopped before its first item, which is still an honest attribution; total is stamped before the loop so this reports 0/N rather than a 0/0 that would read as "never ran". Reason a pair is missing, not a scanned of zero.

    • tg checkpoint undo --json distinguishes a MISSING checkpoint from a CORRUPT one. error: "checkpoint_not_found" means the record could not be resolved. error: "checkpoint_corrupt" (added in this change) means the record WAS found and its snapshot blobs are missing or unreadable, so undo refused before touching a single working-tree file. Both exit 1. Before this, every undo failure reported checkpoint_not_found, which sent the reader hunting a checkpoint that was sitting right there and hid the only fact that mattered -- the snapshot cannot restore the tree. Treat this as ADDITIVE: a consumer that only knows checkpoint_not_found still sees ok: false and a human-readable detail, and the new value appears exactly where the old one was wrong.

    • tg checkpoint create [PATH] --label TEXT accepts an optional trimmed label of 1-120 printable Unicode characters. The label is carried in create/list JSON and human-readable list output, and is persisted in both checkpoint metadata and index.json; omitted labels are null in new records and absent or malformed stored labels load as null without hiding the checkpoint. Labels may repeat and never select restoration: the CLI retains its checkpoint-ID and --last forms, while MCP undo requires the checkpoint ID. MCP tg_checkpoint_create and tg_checkpoint(action="create") accept the same label; supplying it to meta-tool list or undo returns error.code = "invalid_input". Printable strings are preserved literally over MCP, including "null", numeric text, quoted text and JSON-shaped arrays or objects. Non-text values passed directly to the Python handler return invalid_input; over MCP, schema-invalid types are rejected by protocol argument validation (isError) before the handler runs. Invalid text that reaches the handler returns structured invalid_input. The storage version remains v1. Older clients that rewrite the index may discard labels they do not understand.

    8. EvidenceReceipt signing (tg evidence emit --sign / tg evidence verify)

    tg evidence emit always attaches a top-level receipt_sha256 -- a keyless SHA-256 integrity/dedup/chain digest, present whether or not the receipt is signed. Passing --sign additionally attaches signing and signature blocks; passing --previous <path> attaches previous_receipt_sha256 independent of --sign. - Algorithm: Ed25519 (cryptography's Ed25519PrivateKey/Ed25519PublicKey), chosen because a downstream verifier (for example an external service) is a separate trust domain from the machine that emits receipts -- an asymmetric signature lets it verify without ever holding a key that could forge one. tg audit's HMAC-SHA256 (audit_manifest.py) remains correct for its own same-operator local tamper-evidence use case. - Canonicalization (tg-canonical-json-v1): json.dumps(receipt_without_signature_and_receipt_sha256, sort_keys=True, separators=(",", ":"), ensure_ascii=True, allow_nan=False).encode("utf-8"). Only the signature and receipt_sha256 fields are excluded from the signed/hashed bytes -- the signing block itself (including its algorithm claim) is signed, so an algorithm-downgrade or public-key-swap attack invalidates both the digest and the signature. receipt_sha256 and the Ed25519 signature are computed over the identical canonical bytes. - Number formatting is CPython-specific (cross-implementation caveat): tg-canonical-json-v1 inherits CPython's json number formatting -- notably its float.__repr__ (shortest round-trip, e.g. 0.1 + 0.2 serializes as 0.30000000000000004) and its arbitrary-precision integer output. This is not RFC 8785 / JCS canonical-number formatting. A verifier written in another runtime (JavaScript / Go) MUST reproduce CPython's exact number serialization to recompute the same canonical bytes, or its digest/signature check will spuriously fail on any receipt containing a non-trivial float. Practical guidance: tg's own receipt fields are simple (small integers, short decimals like a confidence of 0.72, and strings), which round-trip identically across implementations; a downstream verifier should either match CPython number formatting exactly or treat numeric fields with care (and any caller-supplied --cost-json should avoid high-precision floats). A future tg-canonical-json-v2 could adopt JCS if a cross-language verifier needs stricter number canonicalization. - Wire shape when signed: "signing": {"algorithm": "ed25519", "key_id": "sha256:<hex of the raw 32-byte public key>", "public_key": "<base64 raw 32 bytes>", "signed_at": "<RFC3339>", "canonicalization": "tg-canonical-json-v1", "receipt_id": "<uuid4>"} plus "signature": {"value": "<base64 signature>"}. The signature block holds only the raw signature value; the signer's identity lives in the (signed) signing block. - Trust bootstrap (never trust an embedded key for authenticity): tg evidence verify always reports the signer's key fingerprint (key_id), computed from the embedded public key's own bytes -- never from a claimed label. An embedded public key only proves internal self-consistency (anyone can generate a keypair and sign with it); actual authenticity requires an out-of-band pinned key, supplied via repeatable --trusted-key <base64-public-key> or TG_EVIDENCE_TRUSTED_KEYS (comma-separated). --require-trusted fails valid closed unless the embedded key's fingerprint matches a pinned entry (hmac.compare_digest); a trusted-key check against an unsigned receipt is always invalid, mirroring audit_manifest.py's "signing key supplied but manifest unsigned" rule. - Key management: the private key defaults to ~/.tensor-grep/keys/evidence_ed25519.key (per-user home, never the per-repo .tensor-grep/ that tg audit writes to), overridable via --signing-key / TG_EVIDENCE_SIGNING_KEY. tg evidence keygen writes the private key at file mode 0600 via an atomic create-then-rename (refusing to overwrite an existing file or write through a symlink unless --force) and the public key alongside at <path>.pub (0644). tg evidence pubkey prints the public key and key_id for registration with a downstream verifier. - Fail-closed: --sign with no resolvable signing key (or an unavailable cryptography install) exits non-zero and writes no receipt -- it never falls back to emitting an unsigned receipt. Every receipt-file read is size-bounded (rejects a file over a few megabytes) before parsing/hashing: both the primary receipt (tg evidence verify <path>) and the --previous chain file (reachable from both tg evidence verify --previous and tg evidence emit --previous). - Consumer note: signatures do not expire; replay/staleness detection (via receipt_id, signed_at, and the revision.commit_sha/dirty_tree_sha256 repo binding) is the downstream verifier's responsibility, not tg's for a standalone receipt verified directly with tg evidence verify (which has no ref-comparison flag). When a receipt is embedded in a review bundle instead, section 11 below's tg review-bundle verify --against <ref> provides an in-tool, fail-closed freshness check against a caller-supplied git ref -- the CI-gate path this note used to say tg does not provide.

    9. Ledger claims (tg ledger claim / release / list) -- advisory, code-scoped agent coordination (Slice 1)

    tg ledger is a local, ADVISORY, code-scoped agent-to-agent coordination plane. A claim is a lightweight, TTL-expiring, best-effort record that one agent intends to touch a symbol or file -- it is never a lock on an edit. tg ledger claim always succeeds (exit 0) even when a live overlapping claim exists from another agent; overlap information is reported for the caller to act on, and tg never refuses or blocks an edit because of it. State lives at <canonical-repo-root>/.tensor-grep/ledger/claims/index.json and is created only by the first claim in a repo (default-inert: list/release never create it).

    Status: EXPERIMENTAL / preview (Slice 1), unlike section 8's EvidenceReceipt above -- the CLI surface and JSON schema documented in this section may change in a minor release. tg ledger --help and each subcommand's own --help are marked EXPERIMENTAL (Slice 1) for the same reason, mirroring how tg find's docstring is prefixed EXPERIMENTAL:.

    • PATH scoping : claim/release/list all canonicalize PATH to the nearest .git ancestor -- the SAME shared claims index for one repository, regardless of which subtree of it PATH names (.git is the one unambiguous, universally-understood repo-boundary signal; falls back to PATH taken literally, unchanged, when no .git is found, so a non-git working directory is not regressed). PATH is now preserved as the claim's scope (root-relative, POSIX-normalized -- Windows separators, a leading ./, and a trailing / are all normalized for free) instead of being (mis)used as the physical storage location. This canonicalization applies on the SAME terms to Slice 2 (record/find, below) as well -- both slices share the one _ledger_physical_root derivation (derive the current call-site membership from grep -n "_ledger_physical_root(path)" src/tensor_grep/cli/ledger_store.py, never from an enumerated list -- a name list goes stale the moment a new entry point is added); the non-git literal-PATH fallback described above is likewise shared by both slices, unchanged. Migration honesty: a claim written by a PRE-fix version through a subtree PATH lives in that subtree's old physical store (<subtree>/.tensor-grep/ledger/), which post-fix commands never read or write again -- it becomes invisible to list and unreleasable by release (no crash; the orphaned index simply sits as a dead file whose claims are TTL-expired within their own TTL window, default 15 minutes). During that window, a release targeting such a pre-fix claim reports unmatched_reason and a live_claims_elsewhere drawn from the NEW canonical store -- it cannot see the orphan -- so a just-upgraded agent should simply let the old claim expire rather than chase the release. Do not delete the whole .tensor-grep/ directory to remove an old ledger store: it may also contain sessions and durable checkpoints.
    • Exit-code contract (two states only, not the three-state symbol-command contract in section 3 above): 0 = the command completed and its JSON/text output can be trusted, including a claim with non-empty overlaps, a release that matched zero claims, and a list with zero live claims -- none of those are errors. 2 = a fail-closed condition fired and nothing was written: a claims-index lock-acquire timeout, a symlink at the index destination, a --files entry that resolves outside the repo root (../..., an absolute path, or a symlink escape), a corrupt or oversized on-disk index, or missing required arguments (claim with neither --symbol nor --files; release with neither --claim-id nor --symbol). There is no exit 1 for this command family.
    • Claim record shape: {ledger_schema_version, kind: "claim", claim_id, agent_id, symbols, files, scope, intent, note, created_at, expires_at, ttl_seconds, revision}. claim_id is claim-<UTC-compact-timestamp>-<8-hex>. scope is PATH normalized against the canonicalized repo root -- "." for the repo root itself, e.g. "core/hooks" for a subtree (see "PATH scoping" above; an entry read back from a pre-fix on-disk record with no scope key at all is stamped "." on the way out, never dropped). revision is the same {status, commit_sha, branch, dirty, dirty_tree_sha256, dirty_file_count} / {status: "unavailable", reason} shape section 8's EvidenceReceipt uses (_repo_revision_identity) -- captured for free at claim time so a caller can tell whether an overlapping claim was filed against the same commit.
    • tg ledger claim PATH [--symbol S ...] [--files a,b] [--intent edit] [--ttl SECONDS] [--agent-id ID] [--note TEXT] [--json]: --symbol is repeatable; --files is one comma-separated value of root-relative paths (traversal-refused, per the exit-2 contract above, against the canonicalized repo root). Requires at least one --symbol or --files entry. Response JSON: {version, schema_version, routing_backend: "Ledger", routing_reason: "ledger-claim", sidecar_used: false, ledger_schema_version, advisory: true, claim: {...}, overlaps: [...]}. overlaps lists LIVE (non-expired) claims whose symbols/files literally intersect the new claim, and is never scope-filtered (a symbol/file overlap matters regardless of which subtree each claimant used). Self-suppression -- dropping the caller's OWN other claims, since an agent overlapping itself is not a coordination conflict -- applies ONLY when the caller has a real identity. The default agent_id is the literal sentinel "anonymous", which is the ABSENCE of an identity rather than one, so two zero-config agents both filed as "anonymous" DO see each other's overlaps (ledger_store._find_overlaps gates its suppression on agent_id != _DEFAULT_AGENT_ID; pinned by tests/unit/test_anonymous_claims_are_not_one_agent.py). Each overlap entry is {claim_id, agent_id, symbols, files, intent, expires_at, revision_matches}; revision_matches is true/false only when both sides have a resolved git identity, and null (never fabricated) when either side's revision capture came back unavailable.
    • tg ledger release PATH (--claim-id ID | --symbol S) [--agent-id ID] [--json]: --claim-id releases an exact claim regardless of which agent owns it (the opaque id itself is the authorization -- e.g. an orchestrator garbage-collecting a crashed sub-agent's claim). --symbol releases only the resolved --agent-id's OWN live claim(s) covering that symbol, so a common/guessable symbol name can never release another agent's claim by accident. PATH only resolves WHICH repository's canonical claims index this call operates on (see "PATH scoping" above) -- it does NOT filter which claim matches (deliberately unchanged from the pre-fix contract, unlike list below: adding scope-rollup matching to release could let a call silently drop an unrelated sibling agent's claim just because it shares a symbol name under a broader/ancestor scope). Response JSON: {..., routing_reason: "ledger-release", released: [...], released_count, listed_scope, unmatched_reason, live_claims_elsewhere: [...], live_claims_elsewhere_count, live_claims_elsewhere_truncated}. Releasing zero matching claims (already released, already expired, or never existed) is not an error and does not change the exit code -- but unmatched_reason (a short, human-readable string) and live_claims_elsewhere (bounded to 10 entries, each {claim_id, agent_id, scope, symbols, files, intent, expires_at}, with live_claims_elsewhere_count as the true total and live_claims_elsewhere_truncated set when the count exceeds what is shown) are now populated so a wrong --claim-id/--symbol is self-diagnosing instead of an indistinguishable bare released_count: 0. listed_scope is PATH normalized the same way a claim's scope is. All five of these fields are None/empty/0/false (as appropriate) when released_count > 0.
    • tg ledger list PATH [--symbol S] [--agent-id ID] [--json]: pure read -- prunes expired entries for display only and never writes (so list alone can never create .tensor-grep/ledger/). Rolls scope UP: listing a broader/ancestor PATH (e.g. the default ., the repo root) shows every live claim scoped to it OR to any descendant subtree -- e.g. a claim made with tg ledger claim core/hooks shows up in tg ledger list (default .) and in tg ledger list core, but not in tg ledger list docs (a disjoint sibling) and not the other way around (tg ledger list core/hooks/sub does NOT show a claim scoped to core or to . -- rollup is one-directional: a narrower listing never gains visibility into a broader ancestor scope). Containment is segment-wise (lexical), never a raw string-prefix test -- a claim scoped to core/ho does not falsely match a listing of core/hoodie or vice versa. --symbol/--agent-id filters apply AFTER the scope-rollup filter, combined as AND. Response JSON: {..., routing_reason: "ledger-list", claims: [...], count} -- each entry in claims carries its own scope.
    • agent_id resolution: --agent-id (when non-blank) wins; else TG_LEDGER_AGENT_ID; else TG_EVIDENCE_AGENT_ID (shared fallback with tg evidence); else the literal string "anonymous". Recorded verbatim, never inferred from process/user identity. Do not put secrets in --agent-id or --note -- both are written to a plaintext, per-repo, multi-agent-readable JSON file with no access control beyond the filesystem.
    • TTL and expiry: default 900 seconds, overridable per-claim with --ttl or globally via TG_LEDGER_CLAIM_TTL_SECONDS. A dead agent's claim needs no special crash handling -- it simply stops appearing in list/overlap results once expires_at passes; physical removal from disk happens lazily on the next claim/release write (a pure list never rewrites the index). A record with a missing or unparseable expires_at (corrupt write, foreign edit) is treated as already-expired, not as immortal.
    • Concurrency and DoS bounds: every write (claim/release) is a read-modify-write serialized under the same per-root index_lock primitive tg session/tg checkpoint use (cross-process safe, self-healing stale-lock reclaim, no lost inserts under concurrent writers) -- "per-root" now means per CANONICALIZED root, so two tg ledger claim calls for two different subtrees of the SAME repository correctly serialize against each other, while two calls against two genuinely different (non-git, or differently-.git-rooted) directories still do not. The on-disk index is capped at 256 live claims per root (oldest created_at evicted first) as a bound distinct from TTL expiry -- a flood of claims with a long TTL cannot grow the index without limit even though none of them are individually expired yet. The index read is byte-bounded before parsing (8 MiB) as a pre-parse DoS guard.
    • Not yet built (future slices, do not assume present): no MCP tool surface (CLI-only in Slice 1), no task-level or cross-repo coordination, no automatic claim renewal/heartbeat, no enforcement mechanism of any kind -- tg ledger reports; it never blocks, queues, or serializes an actual edit.

    10. Ledger findings (tg ledger record / find) -- content-addressed reuse of computed artifacts (Slice 2)

    tg ledger record/find extend the Slice 1 coordination plane (section 9) with a content-addressed artifact-reuse cache: one agent records an evidence-receipt/blast-radius/context-pack/repo-map artifact it already computed; a sibling agent finds it by symbol and reuses the artifact instead of recomputing -- the artifact reuse mechanism. State lives at <root>/.tensor-grep/ledger/findings/index.json (a separate index from claims' claims/index.json) plus <root>/.tensor-grep/ledger/findings/blobs/<receipt_sha256>.json (one file per DISTINCT artifact, content-addressed and dedup'd -- recording the identical artifact twice writes the same blob path). Created only by the first record in a repo (default-inert: find never creates it, mirroring claims' list). record/find canonicalize PATH to the nearest .git ancestor on the SAME terms as Slice 1 -- see the PATH-scoping bullet in section 9 for the derivation (_ledger_physical_root, membership derived from its call sites, not enumerated); a record/find from a different subtree of the same repository shares the repo-root index, not a separate one.

    Status: EXPERIMENTAL / preview (Slice 2), same posture as section 9 -- CLI surface and JSON schema may change in a minor release. tg ledger record --help / tg ledger find --help are marked EXPERIMENTAL (Slice 2). Default-OFF in the sense that matters: nothing in tg agent/tg edit-plan consults the ledger automatically in this slice -- record/find are explicit-invoke only (automatic consultation is not implemented).

    • PATH scoping — record/find canonicalize on the SAME terms as Slice 1. Both resolve PATH to the nearest .git ancestor via _ledger_physical_root (grep -n "_ledger_physical_root" src/tensor_grep/cli/ledger_store.py for the current call-site membership -- do not enumerate or count the sites here, that list rots the moment a new entry point is added), so tg ledger find ./src sees an artifact recorded at the repo root. Slice 2 was genuinely more path-literal than Slice 1 once; section 9's scoping bullet and this one are now both current. Re-derive the membership from the call sites above rather than trusting either prose bullet by itself: a behaviour that spreads to a new call site does not retroactively update a sentence that enumerated the old ones -- that is what happened here once already.
    • Exit-code contract for record (two states, same shape as section 9's claim/release/list): 0 = the artifact was ingested (or an identical artifact was already present -- dedup is not an error) and nothing else is asserted. 2 = a fail-closed condition fired and nothing was written: missing --receipt, an --artifact-kind outside {blast-radius, evidence-receipt, context-pack, repo-map}, a missing/oversized (>8 MiB)/non-JSON --receipt file, a findings-index lock-acquire timeout, or a write failure.
    • Exit-code contract for find (three states -- distinct from every other tg ledger subcommand, deliberately mirroring the tg defs/callers/blast-radius symbol-command contract in section 3): 0 = at least one returned finding is fresh: true (safe to reuse). 1 = zero returned findings are fresh (recompute) -- this covers both "no finding matched --symbol/--artifact-kind at all" and "matches exist but none are fresh," including when --fresh-only filtered every match away. 2 = a fail-closed condition fired: missing/blank --symbol, a corrupt/oversized findings index, or -- the case unique to find -- a blob that fails its integrity check (see below). A harness branches on this directly: if tg ledger find PATH --symbol S --fresh-only; then reuse the artifact; else compute; fi.
    • Finding record shape: {ledger_schema_version, kind: "finding", finding_id, agent_id, artifact_kind, symbol, receipt_sha256, blob_relpath, signed, key_id, revision, created_at, expires_at, ttl_seconds}. finding_id is finding-<UTC-compact-timestamp>-<8-hex>. receipt_sha256 is tensor_grep.cli.evidence_signing.receipt_digest() computed over the artifact JSON -- the SAME canonical-JSON content-address function tg evidence uses (tg-canonical-json-v1: compact, key-sorted, ASCII-only, signature/receipt_sha256 fields excluded), so a plain (non-receipt) artifact hashes identically regardless of incidental whitespace, and an artifact that already happens to carry its own receipt_sha256/signature fields (a real EvidenceReceipt) is not self-referentially corrupted by them. revision is the same _repo_revision_identity shape sections 8/9 use. signed/key_id are captured at record time from the artifact's own (self-claimed, unverified) signing block presence -- never proof of authenticity by themselves (see the trust-bootstrap rule below).
    • tg ledger record PATH --receipt FILE.json [--artifact-kind K] [--symbol S] [--agent-id ID] [--ttl SECONDS] [--json]: --artifact-kind defaults to evidence-receipt and is validated against the fixed enum at WRITE time (rejects garbage before it enters the store). --receipt is read bounded (refuses over 8 MiB before parsing -- the same "pre-auth unbounded read" DoS guard section 8/9 use elsewhere) and must parse as a JSON object. Response JSON: {version, schema_version, routing_backend: "Ledger", routing_reason: "ledger-record", sidecar_used: false, ledger_schema_version, advisory: true, finding: {...}}.
    • tg ledger find PATH --symbol S [--artifact-kind K] [--fresh-only] [--trusted-key KEY ...] [--json]: --symbol is required (validated in the store, not by Typer, so a missing value still returns the standard {"error": {...}} JSON envelope under --json rather than a bare Click usage error). --artifact-kind, UNLIKE record, is a plain string-equality filter at READ time -- not validated against the enum, so an unrecognized value simply matches nothing rather than erroring. Response JSON: {..., routing_reason: "ledger-find", findings: [...], count, any_fresh}; each entry in findings is the finding record plus fresh: bool and key_trusted: bool | None (null when the finding is unsigned or no --trusted-key/TG_EVIDENCE_TRUSTED_KEYS was supplied).
    • Freshness (revision-primary, never silently served as current): a finding is fresh: true only when BOTH its captured revision and the CURRENT repo's _repo_revision_identity(root) resolved to status: "present" AND their commit_sha AND dirty_tree_sha256 both match exactly -- so a single uncommitted edit anywhere in the tracked/untracked diff (which changes dirty_tree_sha256) flips a finding to fresh: false even on the same commit. An unresolvable revision on EITHER side (not a git repo, git unavailable) fails closed to fresh: false, never fabricated. Both capture (at record time) and the current-state recheck (at find time) exclude the ledger's own .tensor-grep/ledger/ subtree from the dirty-tree computation (_repo_revision_identity(..., exclude_prefixes=(".tensor-grep/ledger",)), mirroring section 8's tg codemap --check self-dirty fix) -- otherwise the very act of recording would make the repo read as dirty against itself and poison every subsequent freshness check. This is a wall-clock-independent check computed fresh on every find call; the TTL below is a separate, secondary backstop.
    • Integrity (fail-closed, never serve tampered data): every finding actually being returned (i.e. surviving the --symbol/--artifact-kind/--fresh-only filters) has its blob read back and its content digest recomputed via receipt_digest; a mismatch (or a missing/oversized/non-JSON blob) raises and the WHOLE find call exits 2 -- it never silently drops the bad finding and returns the rest, and never serves unverified content. A finding excluded by --fresh-only is never integrity-checked (only findings about to be served are). --trusted-key/TG_EVIDENCE_TRUSTED_KEYS additionally re-verifies a signed finding's embedded signature against the CALLER's current trust config (which may differ from whatever was configured at record time) to compute key_trusted; this mirrors section 8's trust-bootstrap rule exactly -- an embedded public key alone proves internal consistency, never authenticity.
    • TTL, cap, and GC: a wall-clock backstop TTL defaults to 86400 seconds (24h; overridable per-record with --ttl or globally via TG_LEDGER_FINDING_TTL_SECONDS) -- deliberately far longer-lived than a claim's 900s default, since a finding is a reusable artifact pointer, not a short-lived coordination signal. The index is capped at 512 live findings per root; total on-disk bytes across all DISTINCT (dedup'd) blobs is separately capped (default 256 MiB, TG_LEDGER_MAX_BLOB_BYTES) since a flood of small findings could stay under the count cap while a few large artifacts still grow disk unboundedly. Either cap evicts the oldest created_at findings first. Every record call prunes TTL-expired findings and garbage-collects any blob no longer referenced by a live finding (a shared/dedup'd blob is kept until its LAST referencing finding is gone).
    • Not yet built (future slices, do not assume present): no automatic tg agent/edit-plan consultation (explicit-invoke only in Slice 2), no MCP tool surface, no manual release/delete for a findings entry (rely on TTL/cap eviction), no cross-repo lookup.

    11. Review bundles (tg review-bundle create / verify) -- evidence-receipt CI gate

    tg review-bundle create packages an audit manifest plus optional scan results, checkpoint metadata, a manifest diff, and (additive) signed EvidenceReceipts into one JSON artifact; tg review-bundle verify re-checks its integrity, signatures, and -- when asked -- receipt trust and freshness against a git ref. This section documents the additive --receipt / --against / --trusted-key / --require-trusted surface that closes the loop between section 8's EvidenceReceipt signing and an actual CI gate.

    • evidence_receipts component (optional, additive): _REVIEW_BUNDLE_COMPONENTS now includes evidence_receipts alongside audit_manifest (required), scan_results, checkpoint_metadata, and diff (all optional). A bundle created without --receipt sets evidence_receipts: null, exactly like the other optional components when their source flag is omitted; a bundle written by a pre-this-feature tg (no evidence_receipts key at all) verifies identically, since the generic per-component checksum loop treats "key absent" and "key present with null" the same way for a non-required component. Adding this component to the existing checksum/bundle_sha256 machinery is sufficient for it to inherit the SAME tamper-evidence every other component already has -- no separate integrity mechanism was added.
    • tg review-bundle create --receipt FILE.json [--receipt FILE2.json ...]: repeatable. Each path is read through evidence_signing.read_receipt_file (the SAME bounded reader -- 5 MB pre-parse DoS guard, JSON-object validation -- tg evidence verify uses; not reimplemented). The parsed receipt objects are embedded verbatim, in argument order, as evidence_receipts. The text-mode summary line's components= list additively includes evidence_receipts when at least one --receipt was supplied; --json output's top-level evidence_receipts key is null when omitted, matching scan_results/checkpoint_metadata/diff.
    • tg review-bundle verify BUNDLE --against REF [--trusted-key KEY ...] [--require-trusted]: for each embedded receipt, re-verifies its digest/signature/trust via evidence_signing.verify_receipt (the identical function tg evidence verify calls -- no separate crypto path) and, only when --against is supplied, its freshness against REF. --trusted-key (repeatable, base64 Ed25519 public key from tg evidence pubkey) and TG_EVIDENCE_TRUSTED_KEYS (comma-separated fallback) behave exactly like section 8's tg evidence verify flags of the same name, including the same stderr warning when a trusted key is supplied without --require-trusted (an untrusted embedded key then still reports valid=true for that receipt's signature check). Response JSON additively carries receipts (a list, one entry per embedded receipt, {index, receipt_sha256, signature: {...same shape tg evidence verify returns...}, freshness: {...only when --against was given...}, valid}) and, only when --against was supplied, top-level against: {ref, resolved_commit_sha, valid, error}. Every receipt's valid and (when applicable) against.valid are ANDed into the bundle's existing top-level valid; because review-bundle verify --json already exits 1 whenever valid is false (section-3-style H1 contract, pre-existing), an unsigned/untrusted/tampered/stale/unresolvable-ref receipt fails the whole command with no new exit-code logic.
    • Ref resolution is fail-closed, never bundle-path-derived: --against REF is resolved via git rev-parse --verify REF^{commit} run against the verifying process's OWN current working directory (e.g. the CI job's checkout) -- never a path embedded in the (attacker-influenceable) bundle JSON, which would let a tampered bundle redirect ref resolution. An unresolvable ref (typo, ref not fetched, not a git repository, git missing or timing out) sets against.valid = false with a populated against.error and fails the WHOLE bundle closed (valid = false) even when the bundle carries zero receipts -- there is no "the ref didn't resolve, so skip this check" outcome.
    • Freshness definition (commit + clean tree, not the CI working tree's own dirty-tree hash): a receipt is fresh against a resolved --against commit only when its revision.status == "present", revision.commit_sha equals the resolved commit, AND revision.dirty is false. This deliberately does NOT re-derive and compare a dirty_tree_sha256 against the CI checkout's live working tree the way section 10's ledger-finding freshness check does -- a CI checkout can legitimately be sitting on a merge commit (or an actions/checkout ref) whose tree differs from the PR-head tree the receipt was captured against, so comparing tree hashes here would falsely flag every receipt stale. A receipt captured against a dirty working tree fails regardless of commit match, since a dirty capture is not reproducible from a commit alone.
    • CRITICAL CI wiring trap -- use the PR head SHA, never $GITHUB_SHA: in a GitHub Actions pull_request workflow, $GITHUB_SHA (and the default actions/checkout ref) resolves to an ephemeral merge commit of the PR branch into the base branch, not the PR's actual head commit. Passing --against "$GITHUB_SHA" (or omitting an explicit ref: on actions/checkout) means every embedded receipt's revision.commit_sha -- captured against the real PR head -- will NEVER match, and the gate fails RED on every single PR regardless of whether the evidence is actually fresh. The correct value is the pull_request event's head SHA (github.event.pull_request.head.sha), paired with an explicit actions/checkout ref: ${{ github.event.pull_request.head.sha }} so the checkout the receipt was captured against and the ref verified against are the same commit. See docs/enterprise_review_bundle_ci.md for a full worked CI recipe.
    • CRITICAL presence caveat -- integrity alone does NOT prove evidence is present: a bundle with evidence_receipts null, absent, or [] verifies valid = true by default (an empty/missing OPTIONAL component is valid, exactly like scan_results/checkpoint_metadata/diff). Because the keyless checksums and bundle_sha256 are plain SHA-256 (no signing key required to recompute them), an author with write access to review-bundle.json can strip every embedded receipt, recompute those checksums to stay internally consistent, and the bundle will still verify green with no evidence at all -- integrity alone only proves "this JSON file is internally self-consistent," not "genuine evidence is present." --min-receipts and --expect-key below are the opt-in policy levers that close this: only read a passing tg review-bundle verify as proof genuine evidence is present when the gate was run with --min-receipts >= 1 (and --expect-key when a specific signer must be represented).
    • tg review-bundle verify BUNDLE --min-receipts N (default 0 = no enforcement, back-compat): after the existing checks above are computed, if the count of embedded receipts that are present, well-formed, AND pass signature/trust/freshness verification (i.e. each has receipts[].valid = true under whatever --require-trusted/--against were also passed) is less than N, verification fails closed (valid = false) with a reason string "policy requires >=N valid evidence receipts; found M". N = 0 (the default) is always trivially satisfied and adds no new top-level field -- byte-identical output to before this flag existed.
    • tg review-bundle verify BUNDLE --expect-key KEY_ID (repeatable, default none): requires that at least one valid, embedded receipt was signed by each named key_id (the SAME sha256:<hex> fingerprint format tg evidence pubkey and receipts[].signature.key_id already use -- reused, not reinvented). A named key with no matching valid receipt fails verification closed with a reason string naming the missing key_id. This pins WHICH signer(s) are REQUIRED to be represented, distinct from --trusted-key (section 8), which pins which signers are cryptographically TRUSTED at all -- an org might trust several keys (--trusted-key) while requiring evidence specifically from one of them (--expect-key).
    • policy JSON field (additive, only present when --min-receipts > 0 or --expect-key is used): {min_receipts, valid_receipt_count, min_receipts_satisfied, expect_key_ids, missing_expect_key_ids, expect_keys_satisfied, valid, reasons}. policy.valid is ANDed into the bundle's top-level valid exactly like every other check family in this section; omitting both flags omits this field entirely (not merely a null/trivial value), so a caller that never opts in sees byte-identical JSON to before this hardening.
    • What this does NOT change: tg review-bundle create/verify without --receipt/--against/--min-receipts/--expect-key are byte-for-byte the same contract as before this section -- no required component changed, no exit-code semantics changed, no existing field was renamed or removed. tg evidence emit/verify (section 8) are unchanged; --against/--min-receipts/--expect-key are review-bundle-only surfaces, not new tg evidence verify flags.
