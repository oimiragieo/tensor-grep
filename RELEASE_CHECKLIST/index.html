    Release Checklist

    This checklist reflects the current enterprise release pipeline:

    • CI on main runs formatting/linting, Python + Rust matrices, GPU hooks, benchmark regression, release/package-manager readiness checks.
    • Semantic Release on green main creates the version/tag/release commit.
    • PyPI publish is OIDC-based and runs only when the computed release version is not already on PyPI.
    • Release asset/version consistency is enforced by scripts/validate_release_assets.py.

    0. Enterprise-ready evidence

    Before calling a release enterprise-ready, confirm the exact release commit has:

    • green CI on the same commit that semantic-release tagged
    • installer-critical GitHub release assets and CHECKSUMS.txt present on the GitHub release
    • SBOMs, provenance, and signing metadata present when the release path produces them
    • package-manager bundle validation complete
    • public docs aligned:
    • docs/SUPPORT_MATRIX.md
    • docs/CONTRACTS.md
    • docs/HOTFIX_PROCEDURE.md
    • docs/EXPERIMENTAL.md
    • operator runbooks aligned with the shipped behavior

    1. Pre-merge requirements

    1. Sync local branch: 
      git checkout main
git pull --rebase origin main
    2. Confirm version-bearing files are aligned:
    3. pyproject.toml
    4. rust_core/Cargo.toml
    5. npm/package.json
    6. scripts/tensor-grep.rb
    7. scripts/oimiragieo.tensor-grep.yaml
    8. Run local release consistency guard: 
      uv run python scripts/validate_release_assets.py
    9. Run local quality gates: 
      uv run ruff check .
uv run ruff format --check --preview .
uv run mypy src/tensor_grep
uv run pytest tests -v --tb=short
    10. Set the PR title to the intended semantic-release bump so squash merge can drive versioning:
    11. feat: ... -> minor
    12. fix: ... or perf: ... -> patch
    13. feat!: ... / fix!: ... -> major
    14. docs: ..., test: ..., chore: ..., ci: ..., build: ... -> no release
    15. Merge release-bearing PRs with Squash and merge so the validated PR title becomes the commit subject on main.

    2. CI gate requirements on main

    1. Push to main only after local checks pass.
    2. Ensure all required jobs are green:
    3. release-intent on pull requests
    4. Formatting & Linting
    5. release-readiness
    6. package-manager-readiness
    7. test-python matrix
    8. test-rust-core matrix
    9. test-gpu-nvidia
    10. benchmark-regression
    11. Confirm no benchmark regression gate failure.

    3. Release and publication flow

    1. Do not manually bump tags when semantic-release is active.
    2. A branch push or open PR starts PR CI only. It is not a release, not a released version, and not complete release state.
    3. Release versioning starts only after a release-bearing PR is squash-merged to main, because semantic-release reads the final main commit subject.
    4. Let the Semantic Release job infer the next version from the squash-merge commit title created from the PR title.
    5. Let the Semantic Release job create:
    6. release commit
    7. Git tag vX.Y.Z
    8. GitHub release metadata Main CI then uploads installer-critical GitHub release assets to that tag before publish-pypi is allowed to run.
    9. Fetch the release commit before local final verification: 
      git fetch origin main --tags
git pull --ff-only origin main
      This matters because local main can otherwise remain on the pre-release fix commit while origin/main has already advanced to chore(release): vX.Y.Z [skip ci].
    10. If semantic-release reports released=true, confirm downstream jobs pass:
    11. build-release-native-assets
    12. publish-github-release-assets
    13. release-native macOS amd64 asset is built on macos-15-intel, not macos-latest
    14. If publish_pypi=true, confirm PyPI jobs pass:
    15. build-pypi-wheels
    16. build-pypi-sdist
    17. validate-pypi-artifacts
    18. publish-pypi
    19. publish-success-gate
    20. parity gate step Verify release version parity across tag/assets/PyPI
    21. Confirm registry visibility with API evidence, not only local pip cache: 
      python - << 'PY'
import json, urllib.request
data = json.load(urllib.request.urlopen("https://pypi.org/pypi/tensor-grep/json"))
print(data["info"]["version"])
PY
      python -m pip index versions tensor-grep can lag because of client/cache behavior.
    22. If the installer or update path changed, PyPI/public installer availability is verified before release completion is reported.
    23. On main CI, confirm GitHub release asset verification passes before accepting the release:
    24. publish-github-release-assets
    25. step Verify GitHub release native asset coverage
    26. publish-success-gate step Verify GitHub release native assets for semantic-release version
    27. includes release-native CPU front doors (tg-linux-amd64-cpu, tg-macos-amd64-cpu, tg-windows-amd64-cpu.exe)
    28. tg-macos-amd64-cpu was built on an Intel macOS runner label, currently macos-15-intel
    29. includes required package-manager bundle assets (tensor-grep.rb, oimiragieo.tensor-grep.yaml, PUBLISH_INSTRUCTIONS.md)
    30. includes CHECKSUMS.txt and BUNDLE_CHECKSUMS.txt parity validation
    31. Confirm terminal publish gate is green:
    32. normal semantic-release path: publish-success-gate
    33. manual/backfill tag path: release-success-gate (parity + npm publish + docs deploy)
    34. includes final registry parity re-checks before success confirmation
    35. Verify published version parity:
    36. GitHub tag version equals PyPI latest version
    37. GitHub tag version equals npm/package.json version
    38. npm registry latest equals X.Y.Z (verified by release workflow parity step)

    4. Package-manager distribution finalization

    Detailed operational steps live in docs/package_manager_publish.md.

    1. Homebrew formula readiness:
    2. CI runs ruby -c scripts/tensor-grep.rb.
    3. Ensure formula URL points at https://github.com/oimiragieo/tensor-grep/releases/download/v#{version}/....
    4. Winget manifest readiness:
    5. CI runs winget validate on Windows when available and falls back to Python validator only when validation is unavailable, or when hosted-runner winget reports only the known schema-header URL warning and the stricter Python release-asset validator also passes.
    6. Ensure PackageLocale, PackageVersion, nested Installers[0].InstallerUrl, and Installers[0].InstallerSha256 in scripts/oimiragieo.tensor-grep.yaml are schema-valid for the current release.
    7. Release bundle generation stamps Installers[0].InstallerSha256 from generated artifacts/CHECKSUMS.txt before upload.
    8. CI also builds artifacts/package-manager-bundle and verifies BUNDLE_CHECKSUMS.txt parity in package-manager-readiness.
    9. CI uploads package-manager-bundle-<os> artifacts for operator inspection/download from each green run.
    10. Main CI preflights package-manager bundle generation/verification/smoke checks in package-manager-readiness before semantic-release starts.
    11. Post-release operational publish:
    12. Homebrew tap update: open/update PR in tap repo with new formula.
    13. Winget submission: create/update manifest PR in winget-pkgs for new version.
    14. Keep release artifacts canonical:
    15. Build artifacts must map 1:1 to tag version and expected filenames.
    16. Main CI builds release-native CPU front-door binaries from the semantic-release tag only when semantic-release reports released == true, smoke-runs --version/--help, and renames them to the installer URLs.
    17. Non-release main pushes must not reuse the current package version to upload assets to the previous GitHub release.
    18. publish-github-release-assets validates the expected native-front-door filename matrix and emits CHECKSUMS.txt (SHA256) before uploading GitHub release assets.
    19. publish-github-release-assets also generates and publishes package-manager bundle assets (Homebrew formula + Winget manifest + instructions) for repeatable downstream submission.
    20. publish-github-release-assets runs both bundle integrity and content smoke checks before publish:
      • scripts/verify_package_manager_bundle_checksums.py --bundle-dir artifacts/package-manager-bundle
      • scripts/smoke_test_package_manager_bundle.py --bundle-dir artifacts/package-manager-bundle

    5. Rollback runbook

    Use this when a bad release escaped:

    1. Stop forward publishes:
    2. Temporarily disable release workflow or merge a hotfix with skip release in commit message.
    3. If PyPI publication is incorrect:
    4. Publish a patch release with corrected contents (preferred).
    5. Do not rely on deleting artifacts as a primary rollback mechanism.
    6. If GitHub release assets are incorrect:
    7. Rebuild artifacts for the correct tag.
    8. Replace assets in GitHub release and rerun validators.
    9. Package manager rollback:
    10. Homebrew: revert formula in tap to previous known-good version.
    11. Winget: submit manifest update pointing to previous known-good installer.
    12. Incident close-out:
    13. Add root cause + mitigation to CHANGELOG.md and the relevant public technical guide (if architecture-impacting).
    14. Add/adjust CI assertion so the specific failure cannot recur.
